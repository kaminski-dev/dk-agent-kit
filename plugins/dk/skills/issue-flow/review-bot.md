# Review bot

For the session watching a PR whose base a review bot reviews, once the watcher prints the bot's verdict (`dk:issue-flow` step 6), and for step 7's batch PR.

A PR into a base that `workflow.md` lists under **Review bot** gets a review from the bot it names; with no such line, that is `coderabbitai[bot]` on PRs into `main`: the batch PR, or every PR when the base is `main`. The watcher reads the line, so keep the login and the bases in backticks. You fetch the bot's findings yourself, so the maintainer never pastes them. A review counts when its `commit_id` is the head (`headRefOid`) and it has a body or inline comments of its own; a bot review holding only thread replies does not.

1. Read both sources of each review id the watcher printed and list every finding before fixing any. Inline comments: `gh api --paginate "repos/{owner}/{repo}/pulls/<PR>/comments" --jq '.[] | select(.pull_request_review_id == <id> and .user.login == "coderabbitai[bot]" and .in_reply_to_id == null) | {id, path, line, body}'`, with the bot's login from `workflow.md` when it names another. The review body: `gh api "repos/{owner}/{repo}/pulls/<PR>/reviews/<id>" --jq .body`. The body holds findings no inline comment carries (outside diff range, nitpick, follow-up), each headed by its lines: `` `path:12-20` ``, or `` `12-20`: `` under a file name.
2. Work them: on a per-issue PR, fix on its branch and push; on the batch PR, step 7 routes them ([after-merge.md](after-merge.md)). A skipped finding gets its reason on its thread. A body finding has no thread, so its reply is a PR comment naming its file and lines. Each push starts a new round: watch and read again. The rounds follow `dk:code-review`'s **Answer findings** step with the bot as the reviewer: you judge each finding's severity, answer it in the ledger under its comment id (`<review>-<k>` for the k-th body finding), and stop where its round budget says.
